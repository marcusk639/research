**Overall verdict on the priority task:** the ledger's fabrication hypothesis is **REFUTED** for the
core Claude-vs-GPT-vs-Copilot comparison — those four figures (88.6%, 80.0%, 69.2%, 78.9%/83.4%)
are real, independently corroborated, dated leaderboard entries, not invented numbers. But the
hypothesis is **partially CONFIRMED** for the DeepSeek/OpenRouter side of the same tables: no
independent source resolves a "DeepSeek V4" benchmark entry at all, and the Copilot SWE-bench Pro
figure (41.0%) does not match any current data (real figure ~55–56%). The more consequential
finding is not fabrication but **staleness**: every one of the confirmed figures was superseded by
a newer model within weeks to months of the source document's writing, and in at least one case
(Terminal-Bench, C-124) the comparison was already incomplete on the day it was likely written,
because a higher-scoring same-vendor configuration (Claude Fable 5) was already on the same
leaderboard the corpus cites. A benchmark table in a document with no revision date is a snapshot
that expires faster than the document itself.

## Contradiction Findings

### X-01 — Multi-agent fan-out: banned pattern or the corpus's own flagship feature?

**Resolution: these are different patterns, and the evidence does not support treating them as the
same failure mode.**

Anthropic's own June 2025 multi-agent research post — independently confirmed via two channels
(Simon Willison's summary and contemporaneous Slashdot coverage: "Anthropic Deploys Multiple Claude
Agents for 'Research' Tool — Says Coding is Less Parallelizable") — describes a specific
architecture: an orchestrator decomposing a task and spawning **3–5 parallel subagents**, each
running **3+ tools in parallel**, on **breadth-first, decomposable** work. That is the pattern the
corpus's Position A (C-069, "large multi-agent fan-out") targets, and the 15x-token-cost /
poor-fit-for-coding findings are Anthropic's own, about that specific shape of parallelism.

Position B's "Judge-Builder loop" is architecturally different: one Builder produces code, one
Judge critiques it **sequentially**, and the Builder revises before a human looks at the file. This
is not decomposition of an interdependent task across many parallel workers — it is a two-agent,
mostly-sequential review pipeline. Critically, **Anthropic's own current best-practices
documentation recommends almost exactly this pattern** under the name "Writer/Reviewer": _"use a
Writer/Reviewer pattern... A fresh context improves code review since Claude won't be biased
toward code it just wrote."_ This is the same primary source (code.claude.com/docs/en/best-practices,
fetched in full) that supplies the corpus's own C-048 and C-075.

So the "researchable question" resolves: a two-model Builder/Judge loop is not the anti-pattern
Anthropic warns about; it is closer to a pattern Anthropic itself endorses. What the evidence does
**not** settle — because no controlled study was found — is whether the _specific_ implementation
in `workflow-plan-v2.md` (Judge running on a cheap model, auto-triggering before every PR, with a
fixed JSON schema) measurably outperforms a simpler single-reviewer-subagent pass on defect-catch
rate or net review-time savings. That comparison has no data on either side; treat it as an open
question, not a resolved one.

### X-03 — Ceremony level: "dumbest thing that works" vs. mandatory context/spec infrastructure

**Resolution: genuinely unresolved — no reliable evidence found for the specific break-even claim,
and the load-bearing "40% token reduction" figure for `AI.md`-style context files could not be
corroborated by any independent source.** (That specific figure, C-107, belongs to W4's docket, but
it directly determines whether X-03's Position B has real evidentiary weight, so it's worth flagging
here: no external source was found substantiating a 40% reduction from a root context file, in this
or any adjacent search.)

What the evidence does show: spec-kit's real, verified growth to 111k+ GitHub stars (C-053, up from
93k) indicates substantial practitioner adoption of ceremony-heavy, spec-first workflows industry-wide
— which cuts somewhat against the corpus's own "sledgehammer to crack a nut" framing of heavy spec
tooling as a general judgment, even though that framing may still be correct for a specific solo
operator's specific task mix. Kiro's EARS-notation, three-document spec system is real and
substantial ceremony (confirmed, C-054), and Anthropic's own documented interview-then-SPEC.md
pattern (C-018) sits closer to Position B's ceremony than Position A's minimalism — Anthropic's own
docs recommend a middle path (interview for _larger_ features only, skip planning for a change you
"could describe... in one sentence"), which is itself evidence against a single universal answer.
**No study was found that establishes a break-even point in tokens, time, or defect rate between
minimal-ceremony and structured-spec approaches for a solo operator.** This is a genuine gap, not an
oversight — it would require a controlled comparison that, as far as this search could determine,
does not exist in public sources.

### X-06 — The benchmark "winner" flips depending on which benchmark is cited

**Resolution: the two benchmarks measure different things and are not interchangeable, but neither
figure the corpus cites is current, and the specific "28-point lead" claim (C-096) cannot be
validated because one of its two inputs (Copilot at 41.0% SWE-bench Pro) does not match any
current published figure (real figure found: ~55.6%).**

SWE-bench Pro evaluates multi-file, repository-level issue resolution against real GitHub-style
tasks across 41 professional repositories (Scale AI's benchmark). Terminal-Bench 2.1 evaluates
broader agentic terminal competence — compiling code, training models, server setup, system
administration, security tasks, and data-science workflows, not solely code-repair tasks. SWE-bench
Pro is the closer proxy for "multi-file, interdependent professional coding work" as the corpus's
own reconciliation (C-162) asserts — but that assertion, checked here, has **no independent
citation supporting it**; it is the corpus's own unsupported methodological argument, even though it
is a defensible one given what each benchmark actually measures.

Independent of which benchmark is more relevant, **neither of the corpus's cited configurations is
current as of 2026-08-01.** On SWE-bench Pro, "Claude Opus 4.8" (69.2%, real at the time) has been
surpassed by Claude Fable 5 (80.3%) on the same tracker. On Terminal-Bench 2.1, both "Claude Code +
Opus 4.8" (78.9%) and "Codex CLI + GPT-5.5" (83.1–83.4%) have been surpassed by GPT-5.6 Sol
(85.77%) and Claude Opus 5 (84.64%) on the same leaderboard (vals.ai, updated 2026-07-31). The
"winner" question the corpus poses has already been overtaken by newer releases from both vendors
— the flip the ledger noticed between v1.md and v2.md is a symptom of undated benchmark snapshots,
not evidence that one document is more correct than the other.

## Gaps

- **No controlled comparison of Judge-Builder vs. fresh-subagent-reviewer vs. large multi-agent
  fan-out exists** on token cost, defect-catch rate, or net review-time savings. All three patterns
  are individually documented; none has been benchmarked against the others. This would require a
  practitioner-run study with a fixed task set and measured outcomes — none was found.
- **No source substantiates the specific "100–150k token" context-degradation threshold** (C-051).
  Anthropic's own docs confirm the mechanism (performance degrades as context fills) but give no
  numeric threshold. Settling this would require Anthropic publishing internal benchmarks of
  quality-vs-context-length, which does not appear to exist publicly.
- **"DeepSeek V4" could not be located as a real, named, benchmarked model** in any source consulted.
  This is either a genuine gap in public English-language benchmark coverage, a naming
  inconsistency in the corpus, or a forward-looking/hypothetical model name. Settling it would
  require checking DeepSeek's own release notes and Chinese-language coverage directly, which was
  out of scope for the search tools available this pass.
- **Amp (Sourcegraph)'s current pricing/billing model was not confirmed.** The claim that it is
  "free, ad-supported" could not be verified or refuted — a direct fetch failed and search budget
  was exhausted before a retry. This is a real gap, not a judgment call.
- **Hermes Agent CLI and Manifest (C-129, C-130) were not independently checked at all** this pass.
  Given the ledger's own note that these are reversed within the same document lineage
  (`workflow-plan-v2.md` explicitly says not to use them), independent verification matters less for
  the operator's decision but the claims remain formally unverified.
- **No practitioner-level data exists comparing minimal-ceremony vs. structured-spec approaches for
  a solo operator specifically** (X-03). All evidence found is either adoption/popularity metrics
  (spec-kit's star count) or single-vendor framing (Kiro's own EARS-notation pitch), neither of
  which answers the break-even question the ledger poses.

## Implications for the Operator

_(Inference only — not evidence. Phase C should treat this as a lead, not a conclusion.)_

- Any document that cites a SWE-bench or Terminal-Bench score without an explicit as-of date should
  be treated as expired on arrival; these boards move on a timescale of weeks, not quarters. A
  "current tool choice" argument built on a benchmark table is a wasting asset from the day it's
  written.
- The corpus's Claude Code mechanics (hooks, worktrees, subagents, skills, Agent Teams cost) are
  unusually well-sourced and match current official docs almost verbatim — this portion of the
  corpus can likely be trusted at face value for _mechanics_, even though the surrounding
  benchmark-driven tool-choice argument cannot.
- The Judge-Builder-vs-fan-out tension (X-01) is resolved architecturally in the operator's favor:
  a Builder/Judge or Writer/Reviewer pattern is not the anti-pattern to avoid. The open question is
  whether the _specific_ implementation cost (extra model call, extra latency, schema maintenance)
  is worth it over a simpler ad hoc reviewer-subagent prompt — that remains genuinely untested.
- The rate-limit landscape (C-067) has been in a state of near-continuous, repeatedly-extended
  promotional flux since May 2026. Any plan that assumes a fixed weekly-cap number should be
  re-checked against Anthropic's current status before being treated as load-bearing.
