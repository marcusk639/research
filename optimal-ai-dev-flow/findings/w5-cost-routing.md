## Contradiction Findings

### X-02 — Three unreconciled routing ratios; is 80/15/5 cost-optimal?

**Evidence assembled:**

1. **Current pricing supports large potential savings from tiered routing in principle.** Opus 4.8 ($5/$25 per MTok) costs roughly 5x Haiku 4.5 ($1/$5) and 1.7x Sonnet 4.6 ($3/$15). DeepSeek V4 Flash on OpenRouter ($0.09/$0.18) costs roughly 1/30th of Sonnet's rate. The _arithmetic potential_ for large savings by routing routine work to cheap models is real and confirmed (Tier A, Claude Platform Docs + OpenRouter model pages).
2. **General routing research shows 40–85% cost reduction is achievable — but not a validated 80/15/5 figure specifically.** Academic and industry sources (RouterBench-style studies, an ICLR-2025 MT-Bench routing paper achieving 85% cost reduction at 95% of GPT-4-Turbo quality via a matrix-factorization router sending 14% of traffic to the strong model, and 2026 industry retrospectives citing 40–65% reductions) all describe _purpose-built, trained routers_ evaluated on chat/MMLU/MT-Bench benchmarks — not a fixed manual 80/15/5 heuristic, and not tested on multi-file coding or research-synthesis workloads. No source in this research pass ties the specific "80% execution / 15% planning / 5% reasoning" split, or its claimed "60–70% cost reduction," to any measured result. This is the same gap the corpus itself never closes.
3. **The single most detailed practitioner data point available (Redelinghuys) ran the opposite pattern of what 80/15/5 (and the competing 70/30 rule) recommend.** He ran ~95% Opus — the most expensive model — and it was cost-effective anyway, _because he was on a flat-rate subscription where token cost is irrelevant below the usage cap._ This is the crux: tiered per-token routing optimizes API/pay-as-you-go spend; it has no bearing on Max-subscription spend, which is flat regardless of model mix. The 80/15/5 rule is a solution to a cost problem (per-token API billing) the operator, on Claude Max, mostly does not have for interactive work. It only becomes relevant for the _separate_ programmatic/Agent-SDK credit pool (post-2026-06-15, C-068) and for genuinely out-of-subscription work (OpenRouter/DeepSeek).
4. **The operator's actual task mix is not coding-dominant.** Per the ledger's excluded-from-verification §2 facts, the operator's real workload skews toward research/knowledge work and multi-project judgment calls, not routine code completion. The 80/15/5 rule's "Execution tier" examples (test stubs, boilerplate, linting, doc reformatting) describe a coding-heavy shop. A research-synthesis task doesn't decompose into "boilerplate" the way a coding task does — there's no equivalent bulk-generation tier for most research/writing work. `workflow-plan.md`'s A/B/C mapping (Judgment/Generation/Bulk, explicitly keyed to the operator's real ~40–50% routine generation / 25–30% multi-file dev / 15–20% research-strategy / 5–10% judgment split) is a better-fitted starting taxonomy for this reason alone — though it is equally unvalidated externally.

**Decision rule (evidence-derived, volume- and mix-keyed):**

- **Under ~$100/mo API-equivalent, any task mix:** No tiered routing infrastructure is justified. Pro ($20) or pay-as-you-go covers it; the hidden costs of routing setup (F-W5-14) exceed the savings.
- **$100–400/mo API-equivalent, code-heavy with genuine bulk/repetitive tasks (100+ similar items):** Max 5x ($100) as backbone; a routing rule pays off only for the narrow slice of tasks that are truly interchangeable-with-a-cheap-model (boilerplate, test stubs, formatting) — not a blanket 80% allocation.
- **$400–2,000+/mo API-equivalent, heavy multi-repo coding:** Max 20x ($200) as backbone remains the strongest single lever (confirmed by ksred's own breakeven table and this operator's documented heavy usage). A thin OpenRouter/DeepSeek escape valve for the _programmatic/Agent-SDK credit pool specifically_ (post-June-2026 billing split, C-068) is where per-token tiered routing is now most relevant — not the interactive Claude Code session, which is flat-rate regardless of model choice.
- **Research/knowledge-work-dominant mix (this operator's actual profile):** Neither 80/15/5 nor the 70/30 split maps onto the task types involved. The A/B/C Judgment/Generation/Bulk framework, recalibrated to the operator's own measured task distribution rather than a coding benchmark's, is the more defensible starting point — with the explicit caveat that it, too, is unvalidated by any external study.
- **Regardless of volume or mix:** never bind a Claude Max/Pro (or ChatGPT Plus) _subscription's own OAuth credential_ into a third-party router (Manifest, Hermes, or similar) — this is a 2026-01/02 Anthropic ToS violation with active technical enforcement (F-W5-08), not a config-overhead trade-off.

**Confidence:** Medium. The pricing and ToS facts are Tier A. The claim that 80/15/5 specifically delivers 60–70% reduction remains genuinely unresolved — the honest answer is "plausible order of magnitude, unvalidated specific ratio," not a verdict either way.

### X-04 — Where the bottleneck actually is (W5 portion; joint with W9)

W5's evidence bears only on the cost side of this question, not the review-capacity side (W9's domain). What the cost evidence shows:

- **The routing-waste diagnosis (C-188) has real support.** Industry sources converge on estimates that 40–60% of production LLM token budgets are spent on tasks a cheaper model could have handled identically — this is a documented, real phenomenon (Tier B, multiple independent sources), not merely a hypothesis.
- **But this does not establish that cost is _the_ bottleneck rather than _a_ bottleneck.** Cost inefficiency and review-capacity limits are not mutually exclusive; nothing in the cost-side evidence resolves which one binds first for this operator, or whether fixing routing (as `workflow-plan-v2.md`'s entire program does) would free up throughput that then runs into the review-capacity ceiling `solo-consultant-workflow.md` describes. That is squarely a W9 question — the workload-volume and reviewer-hours data needed to adjudicate it isn't cost data.
- **One relevant cost-side observation for W9 to weigh:** on Claude Max, most interactive work is _already_ flat-rate — cutting per-token waste there does not change what the operator pays, and does not change throughput (Max hours consumed are the same regardless of which model runs). The routing-waste argument bites hardest on the newly-separated programmatic/Agent-SDK credit pool and on OpenRouter/DeepSeek pay-as-you-go usage — i.e., mostly _unattended, automatable_ work. If most of the operator's actual bottleneck load is _reviewed_ interactive work (the review-capacity thesis's implicit assumption), then optimizing programmatic-credit routing does little to address the reviewer-capacity constraint W9 is evaluating — the two problems may simply not overlap as much as `workflow-plan-v2.md` implies by treating cost as "the" bottleneck.

**Verdict: genuinely mixed, not resolvable from W5 evidence alone.** Cost inefficiency is real and evidenced; whether it is _the_ binding constraint (displacing review capacity) is a capacity/throughput question this workstream cannot settle.

### X-05 — The $800 vs $1,600 discrepancy (resolved)

**Primary source located and read in full:** Kyle Redelinghuys, [ksred.com](https://www.ksred.com), two posts:

- ["I Built a Claude Code Cost Tracker - Was Max Worth It?"](https://www.ksred.com/i-built-a-cost-tracker-for-claude-code-to-see-if-my-subscription-was-worth-it/) — a live, single-month (Feb 2026) cost-tracker snapshot showing 755.7M tokens, $200/mo Max 20x, $1,428–1,538 API-equivalent, with a full cost breakdown (63% cache read, 34% cache write, 4% output, <1% input) and a 90%/74-session Opus dominance.
- ["Claude Code Pricing Guide: Which Plan Saves You Money"](https://www.ksred.com/claude-code-pricing-guide-which-plan-actually-saves-you-money/) — the 8-month, 10-billion-token retrospective that is the actual source of the "$15,000 / $800 / 93%" figures, including the detail that his peak month (July 2025) ran "2.4B tokens with API equivalent of $5,623 on a $100 monthly subscription" — i.e., **he was paying $100/month (Max 5x), not $200/month (Max 20x), for at least part of the 8-month window.**

**Resolution:** The **$800 figure is the primary-source figure and is correct** (or at least is what Redelinghuys himself reports; it was not independently audited by a third party). The **$1,600 figure in v1.md is not a restatement of his data — it is v1.md's own generic model of "a full-time developer," built on the assumption of a flat $200/mo Max 20x for the entire 8-month period** (8 × $200 = $1,600). That assumption doesn't match the primary source: Redelinghuys's own account shows at least part of the period at the $100/mo Max 5x tier, which is consistent with an $800 total (roughly $100/mo average across 8 months) and inconsistent with a constant $200/mo. v1.md appears to have taken the real $15,000 API-equivalent figure from the same underlying case and substituted its own assumed subscription cost rather than the practitioner's actual reported total — producing a plausible-looking but fabricated $1,600/$13,400/89% figure set.

**Confidence: high** that $800 is closer to ground truth and $1,600 is the document artifact. **Confidence: medium** on the exact mechanism (plan-tier switching mid-period) because Redelinghuys's blog does not give a month-by-month plan history — only the Feb-2026 Max-20x snapshot and the July-2025 $100/mo data point, which together are consistent with, but don't fully prove, a Max-5x-to-Max-20x upgrade path.

**Why it matters, confirmed:** this discrepancy sits directly under the corpus's central "subscription arbitrage" argument. It is not a rounding difference — it's evidence that at least one downstream document (v1.md) restated an anecdote with an invented number rather than the source's actual number, and two further documents (`workflow-plan.md`, `workflow-plan-v2.md`) then treated the invented $13,400/89% figure as settled fact without re-checking it.

**F-W5-14: Hidden costs of model routing are real and documented, separate from token-price savings.**

- **Claim:** Practitioner and vendor sources converge on a consistent set of hidden costs: (1) billing/observability opacity when gateways charge for cached or non-processed tokens; (2) debugging becomes materially harder across providers without dedicated tracing/observability tooling; (3) latency variability introduced by extra routing/forwarding hops; (4) silent quality regression — a cheaper model's mistakes surface as downstream defects or client-facing errors days later, not on a cost dashboard, requiring a pre-merge eval gate (cited at 50–500 test cases) to catch safely; (5) prompt/application portability — routing directly to providers from application code means switching models requires code changes in every call site unless a gateway abstraction is already in place. Separately, industry field audits report 40–60% of production LLM token budgets are pure waste (redundant identical calls, or flagship models doing work a fraction of the cost could do identically) — supporting the C-188 routing-waste diagnosis specifically.
- **Evidence tier:** B (industry/vendor blog convergence — several sources have a commercial stake in selling gateway/observability tooling, a bias worth flagging).
- **Support:** [truefoundry.com](https://www.truefoundry.com/blog/llm-cost-optimization), [braintrust.dev](https://www.braintrust.dev/articles/best-llm-gateways-observability-2026), [merge.dev](https://www.merge.dev/blog/llm-routing) — all sampled via search synthesis, not read in full.
- **Date sensitivity:** Medium — the specific waste percentages will drift; the categories of hidden cost are structural and more durable.
- **Confidence:** Medium — directionally consistent across multiple independent-seeming sources, but several are gateway/observability vendors with an obvious stake in "you need our tool to avoid this" framing; treat the specific percentages skeptically.
- **Counter-evidence:** None found contradicting the existence of these costs; the main caveat is vendor self-interest in several sources, not disagreement about the phenomenon.

## Gaps

- **Whether the 50% Claude Code weekly-limit boost (2026-05-13 through its stated 2026-07-13 end date) was extended, made permanent, or allowed to lapse is unknown as of this research date (2026-08-01) — this session found no source dated after 2026-07-13 addressing it.** This is directly relevant to any current quota-based routing decision and should be re-checked before acting on any claim about "current" weekly caps.
- **Copilot Pro/Codex current pricing, Cursor Pro's current credit/overage structure, and Gemini `text-embedding-004`'s current price were not re-verified this session** — the session's web-search budget was exhausted before these could be checked; the corpus's figures for these should be treated as unconfirmed, not confirmed.
- **No independent, controlled study of the specific 80/15/5 (or 70/30, or A/B/C) routing ratio exists.** All routing-cost-reduction research located targets trained/learned routers evaluated on general chat/QA benchmarks (MT-Bench, MMLU), not fixed manual heuristics, and not coding or long-horizon research-synthesis workloads. Settling this would require either (a) an ablation study varying the execution/planning/reasoning split on a representative task sample from this operator's actual workload, or (b) at minimum a published case study from a comparable solo/small-team operator with before/after cost and defect-rate data.
- **Whether Anthropic's per-token pricing (F-W5-01) will still be accurate by the time this report is acted on is not knowable** — Sonnet 5's introductory-to-standard pricing transition alone (2026-08-31) guarantees drift within a month.
- **The entire "subscription arbitrage" argument in this corpus rests on one detailed practitioner data point (Redelinghuys).** No second full-detail case study — with token counts, plan history, and API-equivalent breakdown — was found. This is a structural gap in the underlying evidence base, not something this research pass can close; it would take either Anthropic publishing aggregate usage-value data (unlikely, given the pending lawsuit's subject matter) or additional practitioners publishing comparably detailed cost trackers.
- **No data was found on real defect/quality-regression rates specifically for a solo-operator, research-heavy (non-coding-dominant) workload under tiered routing.** All quality-tradeoff data located is coding- or chat-benchmark-specific; whether cheap-tier routing degrades research-synthesis quality in ways a solo reviewer would catch (or miss) is untested anywhere located.

## Implications for the Operator

_The following are this workstream's inferences, not findings — flagged accordingly._

- Given the flat-rate nature of Max billing (F-W5-02, F-W5-11) and the operator's own heavy multi-project usage, staying on Max 20x as the interactive-work backbone is the best-supported single decision in this whole cost-architecture question — better supported than any specific routing ratio.
- The 80/15/5 rule, adopted wholesale, is solving a per-token-billing problem that doesn't apply to most of the operator's interactive Claude Code usage. Where it _does_ apply — the post-2026-06-15 programmatic/Agent-SDK credit pool, and any OpenRouter/DeepSeek pay-as-you-go usage — a routing policy makes sense, but it should be scoped to that surface, not treated as a general operating rule for all work.
- Do not adopt Manifest's subscription-binding feature or any tool piping a Claude Max/Pro OAuth token into non-Claude-Code contexts — this crossed from "config overhead" to "active ToS violation with enforcement" as of early 2026. This changes the calculus on C-129/C-166/C-172 more than the corpus itself argues: the "skip Hermes/Manifest" reversal already in `workflow-plan-v2.md` turns out to be the right call for an additional reason its author likely didn't know about.
- Given the operator's stated hard constraint (review capacity, not cost, as the likely binding limit — W9's domain), and given that the hidden costs of routing infrastructure (F-W5-14) consume the operator's own scarce hours rather than dollars, any tiered-routing investment should be sized to dollar volumes large enough that the hours spent configuring and debugging it are clearly repaid — this research did not find a validated threshold, but order-of-magnitude reasoning from F-W5-03 suggests routing infrastructure is hard to justify below roughly $150–200/mo in API-equivalent spend outside the Max subscription itself.
- Any cost target expressed as "$X/month blended" in the corpus (C-163, C-174, C-187) should be treated as internally unreliable until re-derived without the flat-fee-shrinks-with-usage error (F-W5-11) — Phase C should not carry these specific dollar figures forward as if verified.
