## Conflicts & gaps

- **Protractor EOL date:** secondary sources say "end of life August 2023" (elinext, dzone search snippets). The primary 2021 RFC (D2-S8) says development ends at Angular 15 (end of 2022). The Angular blog post "Protractor Deprecation Update August 2023" returned 403 and was not read, so the exact August 2023 wording and the HeroDevs support terms are unverified.
- **Angular 9 + Playwright:** Playwright drives any served web app (D2-S5 migration guide; Playwright is listed by `ng e2e` in D2-S7). Whether the Angular CLI Playwright builder schematic installs on an **Angular 9** workspace was not verified. The safe assumption is standalone `@playwright/test` against `ng serve` or a deployed URL, not wired through `ng e2e`.
- **Firebase auth persistence in IndexedDB:** the claim that the Firebase JS SDK stores auth state in IndexedDB is analyst knowledge, inferred from the indexedDB option's stated purpose (search snippet of the 1.51 notes mentions Firebase). The 1.51 release-note text fetched here (E13) does not name Firebase. Alternatives such as emulator REST sign-up plus `signInWithCustomToken` in a setup project were not researched.
- **Playwright Test Agent quality:** the numbers in search snippets ("75%+ healer success", "3–5x faster") trace to blog aggregators (qaskills.sh) attributing them to "Microsoft's benchmarks". No primary Microsoft benchmark was found. Treat those numbers as unsupported.

## Analyst assessment

_(Separate from the sourced claims above.)_

**Web half.** This is the easiest part of the design. Protractor is dead and archived. Playwright is a first-class `ng e2e` option, has an official Protractor migration guide, and does not care that the app is Angular 9. If the CLI builder resists an old workspace, run Playwright standalone against `ng serve`. Firebase integration is well supported:

- `connectAuthEmulator` behind an environment flag.
- A setup project that signs in seeded emulator users.
- `storageState({ indexedDB: true })` to reuse logins.

The emulator's unsigned tokens are a useful safety property: tests cannot accidentally authenticate against production. Playwright Test Agents line up closely with `/generate-e2e`'s pipeline (plan Markdown, generate, heal) and ship a Claude Code loop. One risk needs a guard: the healer can _skip_ tests it decides are "broken". The skill should treat skip-by-healer as a reported finding, never a silent pass.

**Novel approaches, ranked by value per effort:**

1. **(b) Rules-as-oracle** has the best ratio. It is deterministic and cheap through `@firebase/rules-unit-testing`, has a built-in adequacy metric (rule coverage), and has strong analogues (Schemathesis, XACML mutation). As far as this search could find, it is new for Firestore. It catches authorization bugs that UI-only E2E tests structurally miss.
2. **(a) Exploration to cross-check the code-derived spec.** This is proven, and the Playwright planner already provides it for web.
3. **(f) LLM-built state model with deterministic path enumeration.** This is the most interesting differentiator. It turns "comprehensive" into a checkable claim (uncovered transitions are listed). It is unproven end-to-end and needs model review.
4. **(c) Web-vs-mobile differential testing on Firestore end state.** This is cheap once (b) and both suites exist, and WARDroid shows client-validation drift is a real, common bug class. It is still speculative.
5. **(d) Telemetry mining.** Use it for prioritization only, and only after a PHI review, given the recovery/healthcare domain.
6. **(e) Vision oracles.** Advisory only. Even the vendor that ships `assertWithAI` makes it non-blocking by default.

Overall: build the deterministic oracles (rules, Firestore state, testIDs) first, and put LLM judgment in planning and healing, not in pass/fail.
